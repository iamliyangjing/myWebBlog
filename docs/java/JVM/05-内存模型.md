# JVM 内存模型（JMM）详解

> 本文档详细讲解 Java 内存模型（JMM）的三大特性、volatile 和 synchronized 原理、happens-before 原则等

## 1. 内存模型概述

### 1.1 为什么需要内存模型？

现代计算机的内存架构：

```
┌─────────────────────────────────────────────────────────────────┐
│                    现代计算机内存架构                            │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│    CPU 1        CPU 2        CPU 3        CPU 4                │
│  ┌───────┐    ┌───────┐    ┌───────┐    ┌───────┐            │
│  │  核   │    │  核   │    │  核   │    │  核   │            │
│  │  L1   │    │  L1   │    │  L1   │    │  L1   │            │
│  │ 缓存  │    │ 缓存  │    │ 缓存  │    │ 缓存  │            │
│  └───┬───┘    └───┬───┘    └───┬───┘    └───┬───┘            │
│      │            │            │            │                  │
│  ┌───┴────────────┴────────────┴────────────┴───┐            │
│  │                  L2 缓存                      │            │
│  └───────────────────┬───────────────────────────┘            │
│                      │                                         │
│  ┌───────────────────┴───────────────────────────┐            │
│  │                  L3 缓存                      │            │
│  └───────────────────┬───────────────────────────┘            │
│                      │                                         │
│  ┌───────────────────┴───────────────────────────┐            │
│  │                主内存 (RAM)                   │            │
│  └───────────────────────────────────────────────┘            │
│                                                                 │
│  问题：                                                        │
│  - 每个 CPU 核心都有独立缓存                                  │
│  - 缓存与主内存数据可能不一致                                 │
│  - 程序运行速度与内存访问速度不匹配                           │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### 1.2 Java 内存模型（JMM）

JMM（Java Memory Model）定义了 Java 程序中各种变量的访问规则，以及在并发环境下如何保证变量的可见性、原子性和有序性。

```
┌─────────────────────────────────────────────────────────────────┐
│                    JMM 结构                                     │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│    ┌──────────────────────────────────────────────────────┐    │
│    │                      主内存                         │    │
│    │                   （所有线程共享）                    │    │
│    │                                                      │    │
│    │    ┌─────────┐  ┌─────────┐  ┌─────────┐           │    │
│    │    │变量 A   │  │变量 B   │  │变量 C   │           │    │
│    │    └─────────┘  └─────────┘  └─────────┘           │    │
│    └───────────────────────┬────────────────────────────┘    │
│                            │                                  │
│          ┌─────────────────┼─────────────────┐              │
│          │                 │                 │              │
│    ┌─────┴─────┐    ┌─────┴─────┐    ┌─────┴─────┐         │
│    │   线程 1   │    │   线程 2   │    │   线程 3   │         │
│    │ ┌───────┐  │    │ ┌───────┐  │    │ ┌───────┐  │         │
│    │ │工作内存│  │    │ │工作内存│  │    │ │工作内存│  │         │
│    │ │(CPU缓存)│ │    │ │(CPU缓存)│ │    │ │(CPU缓存)│ │         │
│    │ └───────┘  │    │ └───────┘  │    │ └───────┘  │         │
│    └────────────┘    └────────────┘    └────────────┘         │
│                                                                 │
│  - 主内存：所有线程共享的内存区域                              │
│  - 工作内存：每个线程私有的内存区域，存储主内存数据的副本       │
│  - 线程间通信：通过主内存进行                                  │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

## 2. JMM 三大特性

### 2.1 可见性（Visibility）

#### 定义

可见性是指**一个线程对共享变量的修改，能够及时地被其他线程看到**。

#### 问题产生

```
┌─────────────────────────────────────────────────────────────────┐
│                      可见性问题                                 │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  主内存: flag = false                                          │
│                                                                 │
│  ┌──────────────────┐     ┌──────────────────┐                │
│  │    线程 A        │     │    线程 B        │                │
│  │ ┌──────────────┐ │     │ ┌──────────────┐ │                │
│  │ │ flag = false │ │     │ │ 读取 flag    │ │ ← 可能读到旧值  │
│  │ │  (缓存中)    │ │     │ │  (缓存中)    │ │                │
│  │ └──────────────┘ │     │ └──────────────┘ │                │
│  │                  │     │                  │                │
│  │ flag = true     │ ──→ │                  │                │
│  │ (写入缓存)      │     │                  │                │
│  └──────────────────┘     └──────────────────┘                │
│                                                                 │
│  线程 B 仍然看到 flag = false，这就是可见性问题                │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

#### 解决方案

- **volatile**：保证可见性
- **synchronized**：unlock 前将变量写回主内存
- **final**：final 字段在构造函数完成后对所有线程可见

### 2.2 原子性（Atomicity）

#### 定义

原子性是指**一个操作或者多个操作要么全部执行并且执行的过程不会被任何因素打断，要么就根本不执行**。

#### 问题产生

```java
// i++ 不是原子操作
i++; // 实际包含 3 步操作：
// 1. 读取 i 的值
// 2. 计算 i + 1
// 3. 将结果写回 i
```

```
┌─────────────────────────────────────────────────────────────────┐
│                      原子性问题                                 │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  线程 A: i++ (读取 i=0, 计算 1, 写回 i=1)                     │
│  线程 B: i++ (读取 i=0, 计算 1, 写回 i=1)                     │
│                                                                 │
│  期望结果: i = 2                                               │
│  实际结果: i = 1  ← 丢失了一次更新                             │
│                                                                 │
│  时间线:                                                        │
│  ┌────┬────┬────┬────┬────┬────┐                             │
│  │ T0 │ T1 │ T2 │ T3 │ T4 │ T5 │                             │
│  ├───┼────┼────┼────┼────┼────┤                             │
│  │ A: │read│    │calc│    │write│                            │
│  │    │i=0 │    │ i+1│    │ i=1│                            │
│  ├───┼────┼────┼────┼────┼────┤                             │
│  │ B: │    │read│    │calc│    │write│                        │
│  │    │    │i=0 │    │ i+1│    │ i=1│                        │
│  └────┴────┴────┴────┴────┴────┘                             │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

#### 解决方案

- **synchronized**：保证原子性
- **Lock**：保证原子性
- **AtomicInteger 等原子类**：保证原子性

#### 哪些操作是原子的？

| 操作 | 原子性 |
|------|--------|
| 基本类型的读写 | 是 |
| 引用类型的读写 | 是 |
| synchronized 修饰的方法/代码块 | 是 |
| volatile 修饰的 long/double（JDK 8+） | 是 |
| i++ | 否 |
| ++i | 否 |
| i = i + 1 | 否 |

### 2.3 有序性（Ordering）

#### 定义

有序性是指**程序执行的顺序按照代码的先后顺序执行**。

#### 问题产生：指令重排序

```
┌─────────────────────────────────────────────────────────────────┐
│                      指令重排序                                 │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  源代码:                                                        │
│  int a = 1;       // 步骤 1                                    │
│  int b = 2;       // 步骤 2                                    │
│  int c = a + b;   // 步骤 3                                    │
│                                                                 │
│  可能被重排序为:                                                │
│  int b = 2;       // 步骤 2 (先执行)                           │
│  int a = 1;       // 步骤 1 (后执行)                           │
│  int c = a + b;   // 步骤 3 (最后执行)                         │
│                                                                 │
│  重排序原则:                                                    │
│  - 单线程下：结果不变                                           │
│  - 多线程下：可能产生问题                                       │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

#### 解决方案

- **synchronized**：保证有序性
- **volatile**：禁止指令重排序
- **Lock**：保证有序性

## 3. volatile 关键字

### 3.1 volatile 的作用

1. **保证可见性**：写入 volatile 变量后，会立即刷新到主内存；读取前会从主内存读取
2. **禁止指令重排序**：在 volatile 读写前后插入内存屏障，防止重排序

### 3.2 volatile 原理

```
┌─────────────────────────────────────────────────────────────────┐
│                    volatile 原理                                │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  写 volatile 变量:                                             │
│  ┌─────────────────────────────────────────────┐                │
│  │  1. 将新值写入工作内存                      │                │
│  │  2. 立即刷新到主内存                        │                │
│  │  3. 通知其他 CPU 缓存失效                   │                │
│  └─────────────────────────────────────────────┘                │
│                                                                 │
│  读 volatile 变量:                                             │
│  ┌─────────────────────────────────────────────┐                │
│  │  1. 使 CPU 缓存失效                         │                │
│  │  2. 从主内存读取最新值                       │                │
│  │  3. 存入工作内存                            │                │
│  └─────────────────────────────────────────────┘                │
│                                                                 │
│  内存屏障:                                                      │
│  ┌─────────────────────────────────────────────┐                │
│  │  StoreStore │ 写操作前                      │                │
│  │  StoreLoad  │ 写操作后                      │                │
│  │  LoadStore  │ 读操作前                      │                │
│  │  LoadLoad  │ 读操作后                       │                │
│  └─────────────────────────────────────────────┘                │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### 3.3 volatile 不保证原子性

```java
public class VolatileDemo {
    private volatile int count = 0;

    // 不保证原子性！
    public void increment() {
        count++; // 这不是原子操作
    }
}

// 解决方案：使用 synchronized 或 AtomicInteger
public class VolatileDemo {
    private AtomicInteger count = new AtomicInteger(0);

    public void increment() {
        count.incrementAndGet();
    }
}
```

### 3.4 volatile 使用场景

| 场景 | 示例 | 说明 |
|------|------|------|
| 状态标记 | `volatile boolean running = true` | 线程间可见的状态 |
| 双重检查锁 | `private static volatile Instance` | 防止重排序 |
| 防止指令重排序 | 写入后立即可见 | 内存屏障 |

### 3.5 面试提问

> **Q：volatile 如何保证可见性？**
>
> A：写入 volatile 变量时，JMM 会将线程工作内存中的值立即刷新到主内存，并让其他线程的工作内存中的缓存失效。读取 volatile 变量时，会从主内存中读取最新值，而不是从缓存读取。

> **Q：volatile 如何禁止指令重排序？**
>
> A：volatile 会在读写操作前后插入内存屏障。StoreStore 屏障禁止前面的写与后面的写重排序，StoreLoad 屏障禁止 volatile 写与后续读写重排序，LoadLoad 禁止读与读重排序，LoadStore 禁止读与写重排序。

## 4. synchronized 关键字

### 4.1 synchronized 的作用

1. **原子性**：保证代码块或方法同一时间只有一个线程执行
2. **可见性**：unlock 前会将变量刷新到主内存
3. **有序性**：同一锁的 unlock 先行于后续的 lock

### 4.2 synchronized 原理

```
┌─────────────────────────────────────────────────────────────────┐
│                    synchronized 原理                            │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  每个对象有一个监视器锁（Monitor）                              │
│                                                                 │
│  ┌──────────────────┐    ┌──────────────────┐                 │
│  │     线程 A        │    │     线程 B        │                 │
│  │  synchronized(obj) │  │  synchronized(obj) │               │
│  │        ↓          │    │        ↓          │                │
│  │   获取 monitor    │    │   等待获取 monitor │               │
│  │        ↓          │    │        ↓          │                │
│  │   执行同步代码    │    │        ↓          │                │
│  │        ↓          │    │        ↓          │                │
│  │   释放 monitor    │    │   获取 monitor    │                │
│  │                   │    │        ↓          │                │
│  │                   │    │   执行同步代码    │                │
│  └──────────────────┘    └──────────────────┘                 │
│                                                                 │
│  关键字节码:                                                   │
│  - monitorenter    获取锁                                       │
│  - monitorexit     释放锁                                       │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### 4.3 锁的升级过程

HotSpot JVM 中的锁是**可升级**的：

```
┌─────────────────────────────────────────────────────────────────┐
│                    锁升级过程                                    │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│    无锁 ──────→ 偏向锁 ──────→ 轻量级锁 ──────→ 重量级锁       │
│      ↑                                                          │
│      │           竞争加剧                                        │
│      │                                                          │
│      └───────────────────────────────────────┘                  │
│                                                                 │
│  ┌─────────────────────────────────────────────────────────┐   │
│  │  偏向锁 (Biased Lock)                                    │   │
│  │  - 第一次获取锁时，记录线程ID                           │   │
│  │  - 同一线程再次获取锁，只需检查线程ID                   │   │
│  │  - 无锁竞争时性能最优                                    │   │
│  │  - 适用场景：单线程访问                                  │   │
│  │  - 启用参数：-XX:+UseBiasedLocking（默认启用）          │   │
│  └─────────────────────────────────────────────────────────┘   │
│  ┌─────────────────────────────────────────────────────────┐   │
│  │  轻量级锁 (Lightweight Lock)                             │   │
│  │  - 使用 CAS 操作自旋获取锁                              │   │
│  │  - 线程不阻塞                                            │   │
│  │  - 适用场景：少量线程竞争、锁占用时间短                  │   │
│  │  - 缺点：自旋消耗 CPU                                    │   │
│  └─────────────────────────────────────────────────────────┘   │
│  ┌─────────────────────────────────────────────────────────┐   │
│  │  重量级锁 (Heavyweight Lock)                             │   │
│  │  - 使用 ObjectMonitor，线程阻塞                         │   │
│  │  - 不消耗 CPU                                            │   │
│  │  - 适用场景：多线程竞争、锁占用时间长                    │   │
│  └─────────────────────────────────────────────────────────┘   │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### 4.4 synchronized 使用方式

```java
// 1. 修饰实例方法（锁对象是 this）
public synchronized void method() {
    // 同步代码
}

// 2. 修饰静态方法（锁对象是类对象）
public synchronized static void staticMethod() {
    // 同步代码
}

// 3. 修饰代码块（锁对象是指定对象）
public void method() {
    synchronized (this) {
        // 同步代码
    }
}

// 4. 修饰任意对象
private Object lock = new Object();
public void method() {
    synchronized (lock) {
        // 同步代码
    }
}
```

## 5. happens-before 原则

### 5.1 什么是 happens-before？

**JMM 中最核心的原则**：如果操作 A happens-before 操作 B，那么 A 的结果对 B 可见，且 A 的执行顺序在 B 之前。

### 5.2 JMM 定义的 happens-before 规则

```
┌─────────────────────────────────────────────────────────────────┐
│                   happens-before 规则                           │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  1. 程序顺序规则                                               │
│     在同一线程中，按照代码顺序，前面的操作 happens-before 后面的│
│     int a = 1;        // A happens-before B                     │
│     int b = a + 1;    // B                                      │
│                                                                 │
│  2. 监视器锁规则                                               │
│     对同一个锁的 unlock happens-before 后续的 lock              │
│     synchronized (obj) {                                        │
│         // 操作 A                                               │
│     }        // unlock happens-before 下一个 lock               │
│     synchronized (obj) {                                        │
│         // 操作 B                                               │
│     }                                                           │
│                                                                 │
│  3. volatile 变量规则                                          │
│     对 volatile 变量的写 happens-before 后续的读                │
│     volatile boolean ready = true;   // A                      │
│     int result = count;               // B                     │
│     // A happens-before B                                       │
│                                                                 │
│  4. 传递性规则                                                  │
│     如果 A happens-before B，B happens-before C，则 A happens-   │
│     before C                                                    │
│                                                                 │
│  5. 线程启动规则                                                │
│     Thread.start() happens-before 被启动线程中的任何操作        │
│     Thread t = new Thread(() -> {});                           │
│     t.start();                                                  │
│     // t.start() happens-before t 中的任何操作                  │
│                                                                 │
│  6. 线程终止规则                                                │
│     线程中的所有操作 happens-before 其他线程检测到该线程终止    │
│     // 线程 A 中的操作 happens-before 线程 B 检测到 A 终止     │
│                                                                 │
│  7. 线程中断规则                                                │
│     interrupt() 调用 happens-before 被中断线程检测到中断       │
│                                                                 │
│  8. 对象构造规则                                                │
│     构造函数返回 happens-before 对象的 finalize() 开始         │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### 5.3 happens-before 与时间先后无关

> **重要**：happens-before 是**规则**，不是时间上的先后。它关心的是**可见性**，而非执行顺序。

```java
// 示例：不符合 happens-before，但可能正确
int x = 0;
int y = 0;

// 线程 A
x = 1;
y = 2;

// 线程 B
if (y == 2) {
    System.out.println(x);  // 可能输出 0 或 1
}

// 说明：
// 线程 A 中 x=1 和 y=2 符合程序顺序规则
// 但没有 happens-before 关系与线程 B
// 所以线程 B 可能在写入前读取 x
```

## 6. 常见面试问题汇总

### 6.1 基础问题

| 问题 | 答案 |
|------|------|
| JMM 三大特性 | 可见性、原子性、有序性 |
| volatile 作用 | 保证可见性、禁止指令重排序 |
| volatile 不保证什么 | 不保证原子性（如 i++） |
| synchronized 作用 | 保证原子性、可见性、有序性 |
| happens-before 是什么 | 可见性规则，不是时间先后 |

### 6.2 深入问题

> **Q：为什么 long 和 double 不是原子性的？**
>
> A：在 32 位 JVM 中，long 和 double 是 64 位，需要两次 32 位操作。JMM 只要求 long/double 的读写必须是原子（基本操作是原子的），但 volatile 修饰的 long/double 在 JDK 8+ 才保证原子性。

> **Q：synchronized 和 volatile 的区别？**
>
> | 特性 | synchronized | volatile |
> |------|--------------|----------|
> | 原子性 | 保证 | 不保证 |
> | 可见性 | 保证 | 保证 |
> | 有序性 | 保证 | 一定程度保证 |
> | 作用范围 | 方法/代码块 | 变量 |
> | 性能 | 较重 | 轻量 |

> **Q：双重检查锁为什么要用 volatile？**
>
> ```java
> public class Singleton {
>     private static volatile Singleton instance;
>
>     public static Singleton getInstance() {
>         if (instance == null) {
>             synchronized (Singleton.class) {
>                 if (instance == null) {
>                     instance = new Singleton();
>                 }
>             }
>         }
>         return instance;
>     }
> }
> ```
> A：`instance = new Singleton()` 实际分 3 步：
> 1. 分配内存
> 2. 调用构造函数初始化
> 3. 赋值给 instance
>
> 没有 volatile 时，可能发生指令重排序，导致 3 在 2 之前执行。此时其他线程可能获取到未初始化的对象。

> **Q：i++ 为什么不是原子操作？**
>
> A：i++ 实际包含 3 个操作：
> 1. 读取 i 的值
> 2. 计算 i + 1
> 3. 将结果写回 i
>
> 多个线程同时执行时，可能发生数据覆盖，导致结果不正确。

## 7. 总结

### 核心概念图

```
┌─────────────────────────────────────────────────────────────────┐
│                    JMM 核心概念                                 │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  三大特性:                                                      │
│  ┌──────────┬──────────┬──────────┐                           │
│  │ 可见性    │  原子性  │  有序性   │                           │
│  ├──────────┼──────────┼──────────┤                           │
│  │ volatile  │synchronized│ volatile │                          │
│  │synchronized│ Lock    │synchronized│                         │
│  │           │原子类   │  Lock     │                           │
│  └──────────┴──────────┴──────────┘                           │
│                                                                 │
│  happens-before 规则:                                           │
│  - 程序顺序规则                                                 │
│  - 监视器锁规则                                                 │
│  - volatile 变量规则                                            │
│  - 传递性规则                                                   │
│                                                                 │
│  锁升级:                                                        │
│  无锁 → 偏向锁 → 轻量级锁 → 重量级锁                            │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### 最佳实践

1. **可见性问题**：使用 volatile 或 synchronized
2. **原子性问题**：使用 synchronized、Lock 或原子类
3. **有序性问题**：使用 volatile、synchronized 或 Lock
4. **复合操作**：使用原子类或同步机制
5. **单例模式**：使用 volatile + synchronized（双重检查锁）
