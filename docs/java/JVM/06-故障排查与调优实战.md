## 4. GC 调优实战

### 4.1 GC 调优目标

| 目标 | 描述 | 衡量指标 |
|------|------|----------|
| **吞吐量** | 单位时间内处理的任务数 | GC time / Total time |
| **停顿时间** | GC 发生时用户线程暂停时间 | MaxGCPauseMillis |
| **内存占用** | JVM 使用的内存大小 | 堆大小、元空间 |

> **三角形约束**：停顿时间、吞吐量、内存占用三者不可兼得

```
┌─────────────────────────────────────────────────────────────────┐
│                    GC 调优三角约束                               │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│              停顿时间                                            │
│                  ▲                                              │
│                 ╱ ╲                                            │
│                ╱   ╲                                           │
│               ╱     ╲                                          │
│              ╱   ✕   ╲    ← 无法全部最优                       │
│             ╱         ╲                                        │
│            ╱           ╲                                       │
│           ▼─────────────▼                                       │
│       吞吐量  ◄────►  内存占用                                 │
│                                                                 │
│  调优策略：                                                    │
│  - 吞吐量优先: Parallel GC                                     │
│  - 停顿时间优先: CMS、G1                                        │
│  - 平衡: 根据业务特点选择                                       │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### 4.3 常见场景与解决方案

#### 场景1：Minor GC 频繁

```
问题：Minor GC 频繁，每秒或每几分钟一次

原因：
- 新生代太小
- 对象分配速率高

解决方案：
- 增大新生代: -Xmn
- 增大 Eden 区: -XX:SurvivorRatio
- 使用更大堆
```

#### 场景2：Full GC 频繁

```
问题：Full GC 频繁，每小时或每天多次

原因：
- 老年代空间不足
- 对象晋升年龄太小
- 内存泄漏
- 大对象直接进入老年代

解决方案：
- 增大老年代
- 调大晋升年龄: -XX:MaxTenuringThreshold=15
- 使用 CMS: -XX:+UseConcMarkSweepGC
- 使用 G1: -XX:+UseG1GC
- 排查内存泄漏
```

#### 场景3：GC 停顿时间长

```
问题：GC 停顿时间超过业务要求

原因：
- 堆太大
- 收集器不合适
- GC 参数不优

解决方案：
- 选择合适的收集器
- G1: -XX:MaxGCPauseMillis=200
- 减小堆大小
- 使用 ZGC: -XX:+UseZGC
```

## 5. 内存泄漏排查

### 5.1 内存泄漏常见原因

| 类型 | 典型场景 |
|------|----------|
| **集合类** | 静态集合持有对象引用 |
| **单例/静态变量** | 静态字段持有大量对象 |
| **监听器/回调** | 注册监听器未注销 |
| **ThreadLocal** | ThreadLocal 未清理 |
| **资源未关闭** | IO/数据库连接未关闭 |
| **对象重写 equals/hashCode** | 导致 HashMap 无法找到对象 |

### 5.2 排查步骤

```
┌─────────────────────────────────────────────────────────────────┐
│                    内存泄漏排查步骤                              │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  1. 生成堆转储                                                  │
│     jmap -dump:format=b,file=heap.hprof <pid>                   │
│                                                                 │
│  2. 使用 MAT 分析                                              │
│     - Histogram: 查看对象数量和大小                             │
│     - Dominator Tree: 查找内存占用大头                         │
│     - Leak Suspects: 自动检测泄漏                              │
│                                                                 │
│  3. 对比分析                                                    │
│     - 多次 Full GC 后再次 dump                                 │
│     - 对比对象数量变化                                          │
│                                                                 │
│  4. 定位代码                                                    │
│     - 查看对象引用链                                           │
│     - 找到持有引用的代码                                        │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### 5.3 ThreadLocal 内存泄漏案例

```java
// 典型错误代码
public class ThreadLocalDemo {
    // 静态 ThreadLocal，线程退出时未清理
    private static ThreadLocal<Object> local = new ThreadLocal<>();

    public void process() {
        local.set(new LargeObject());  // 设置大对象
        // 没有调用 local.remove()
    }
}

// 解决方案
public class ThreadLocalDemo {
    private static ThreadLocal<Object> local = new ThreadLocal<>();

    public void process() {
        try {
            local.set(new LargeObject());
            // 业务逻辑
        } finally {
            local.remove();  // 清理
        }
    }
}
```

## 6. 实际调优案例

### 6.1 案例1：Web 服务 GC 调优

**业务场景**：电商网站，用户响应时间要求 < 500ms

**问题**：频繁 Full GC，响应时间波动大

**参数调整**：

```bash
# 优化前
-Xms2g -Xmx2g -XX:+UseParallelGC

# 优化后
-server \
-Xms4g -Xmx4g \
-Xmn2g \
-XX:+UseG1GC \
-XX:MaxGCPauseMillis=300 \
-XX:InitiatingHeapOccupancyPercent=45 \
-XX:+HeapDumpOnOutOfMemoryError \
-XX:HeapDumpPath=/var/log/oom.hprof \
-Xlog:gc*=info:file=/var/log/gc.log:time,uptime:filecount=10,filesize=50m
```

**效果**：Full GC 从每天 10+ 次降为 0 次，响应时间稳定在 200ms 以内

### 6.2 案例2：Kafka 消费积压

**业务场景**：大数据处理，Kafka 消费者处理慢

**问题**：GC 停顿导致消费延迟

**参数调整**：

```bash
# 使用 ZGC（超低停顿）
-server \
-Xms8g -Xmx8g \
-XX:+UseZGC \
-XX:ConcGCThreads=4 \
-XX:ParallelGCThreads=8
```

**效果**：GC 停顿时间从 200ms+ 降到 <10ms

### 6.3 案例3：微服务 OOM

**业务场景**：Spring Cloud 微服务

**问题**：Metaspace OOM

**分析**：使用了大量动态代理

**解决方案**：

```bash
# 增大元空间
-XX:MetaspaceSize=256m \
-XX:MaxMetaspaceSize=512m \
# 优化代码，减少动态类生成
```

## 8. 总结

### 排查工具选择

| 场景 | 推荐工具 |
|------|----------|
| 快速查看进程 | jps、jstat |
| 线程问题 | jstack |
| 内存分析 | jmap + MAT |
| GC 问题 | GCViewer、GCEasy |
| 在线诊断 | Arthas |
| 全面分析 | JProfiler |

### 调优原则

1. **先诊断，后调优**：找到问题根源
2. **小步快跑**：每次只改一个参数
3. **记录数据**：保留优化前后对比
4. **回归测试**：确保不影响业务
