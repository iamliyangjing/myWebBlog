# JVM 垃圾回收详解

> 本文档详细讲解 JVM 垃圾回收的核心概念、算法、收集器，是面试重点内容

## 1. 垃圾回收概述

### 1.1 为什么需要 GC？

- Java 虚拟机自动管理内存
- 程序员不需要手动释放对象，避免了内存泄漏
- 但也带来了新的问题：GC 带来的停顿

### 1.2 GC 关注的问题

1. **哪些对象需要回收？**（对象存活判断）
2. **何时回收？**（回收时机）
3. **如何回收？**（回收算法）
4. **如何优化回收性能？**（收集器选择与调优）

---

## 2. 对象存活判断算法

### 2.1 引用计数法

#### 原理

给对象添加一个引用计数器：
- 每有一个地方引用它，计数器 +1
- 引用失效时，计数器 -1
- 计数器为 0 时，表示对象可回收

```
┌─────────────────────────────────────────────────────────────────┐
│                      引用计数法原理                              │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│    对象A ──引用──→ 对象B                                         │
│         ←───────                                                │
│         引用     （A 和 B 相互引用，计数器都不为0）              │
│                                                                 │
│    但实际上这两个对象已经不可达，应该被回收                      │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

#### 缺点

- **无法解决循环引用问题**：A 引用 B，B 引用 A，但它们都无法被外部访问，却无法被回收
- Python 使用引用计数法，但有额外机制解决循环引用

### 2.2 可达性分析算法

#### 原理

通过一系列称为 **GC Roots** 的根对象作为起始点，从这些节点向下搜索，搜索走过的路径称为**引用链**。如果一个对象到 GC Roots 没有任何引用链相连，则该对象可回收。

```
┌─────────────────────────────────────────────────────────────────┐
│                      可达性分析原理                              │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│                      ┌─────────┐                                │
│                      │ GC Root │                                │
│                      └────┬────┘                                │
│                           │                                     │
│              ┌────────────┼────────────┐                        │
│              │            │            │                        │
│              ▼            ▼            ▼                        │
│         ┌────────┐   ┌────────┐   ╳────────╳                    │
│         │  对象  │   │  对象  │   │ 可回收  │ ← 不可达          │
│         │  (存活)│   │  (存活)│   │ 对象   │                    │
│         └────────┘   └────────┘   └────────╳                    │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

#### GC Roots 包含的对象

| 来源 | 说明 |
|------|------|
| 虚拟机栈（栈帧中的本地变量表） | 正在执行的方法中的局部变量 |
| 方法区中类静态属性引用的对象 | 类的 static 修饰的字段 |
| 方法区中常量引用的对象 | 字符串常量池中的引用 |
| 本地方法栈中 JNI 引用的对象 | Native 方法中的对象 |
| JVM 内部引用 | Class 对象、异常对象、类加载器等 |

#### 总结

- **引用计数法**：简单，但无法解决循环引用
- **可达性分析**：主流方案，解决循环引用问题
- Java 使用**可达性分析**算法

## 3. 垃圾回收算法

### 3.1 标记-清除算法（Mark-Sweep）

#### 原理

分为两个阶段：
1. **标记**：标记出所有需要回收的对象
2. **清除**：统一回收所有被标记的对象

```
┌─────────────────────────────────────────────────────────────────┐
│                    标记-清除算法过程                             │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  初始状态：                                                     │
│  ┌───┬───┬───┬───┬───┬───┬───┬───┬───┐                         │
│  │ A │ B │ C │ D │ E │ F │ G │ H │ I │ ← 内存块                 │
│  └───┴───┴───┴───┴───┴───┴───┴───┴───┘                         │
│                                                                 │
│  标记阶段（C, E, H 需要回收）：                                  │
│  ┌───┬───┬───┬───┬───┬───┬───┬───┬───┐                         │
│  │ A │ B │[C]│ D │[E]│ F │ G │[H]│ I │                         │
│  └───┴───┴───┴───┴───┴───┴───┴───┴───┘                         │
│         ↑       ↑           ↑                                  │
│       可达   不可达(回收)  可达   不可达(回收)                   │
│                                                                 │
│  清除阶段：                                                     │
│  ┌───┬───┬───┬───┬───┬───┬───┬───┬───┐                         │
│  │ A │ B │   │ D │   │ F │ G │   │ I │ ← 内存碎片               │
│  └───┴───┴───┴───┴───┴───┴───┴───┴───┘                         │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

#### 缺点

1. **效率不稳定**：标记和清除过程都需要遍历，效率随对象数量增加而降低
2. **内存碎片化**：清除后产生大量不连续内存碎片
3. **空间浪费**：大对象无法分配时提前触发 GC

#### 适用场景

- 老年代（CMS 收集器使用）

---

### 3.2 标记-整理算法（Mark-Compact）

#### 原理

1. **标记**：标记需要回收的对象
2. **整理**：让存活对象向一端移动
3. **清除**：清理掉边界外的内存

```
┌─────────────────────────────────────────────────────────────────┐
│                    标记-整理算法过程                             │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  初始状态：                                                     │
│  ┌───┬───┬───┬───┬───┬───┬───┬───┬───┐                         │
│  │ A │ B │ C │ D │ E │ F │ G │ H │ I │                         │
│  └───┴───┴───┴───┴───┴───┴───┴───┴───┘                         │
│                                                                 │
│  标记阶段（C, E, H 需要回收）：                                  │
│  ┌───┬───┬───┬───┬───┬───┬───┬───┬───┐                         │
│  │ A │ B │[C]│ D │[E]│ F │ G │[H]│ I │                         │
│  └───┴───┴───┴───┴───┴───┴───┴───┴───┘                         │
│                                                                 │
│  整理阶段（存活对象向一端移动）：                                │
│  ┌───┬───┬───┬───┬───┬───┬───┬───┬───┐                         │
│  │ A │ B │ D │ F │ G │ I │   │   │   │                         │
│  └───┴───┴───┴───┴───┴───┴───┴───┴───┘                         │
│        ← ← ← ← ← ← ← ← ← ← ← ← ←                             │
│                                                                 │
│  清除阶段：                                                     │
│  ┌───┬───┬───┬───┬───┬───┬───┬───┬───┐                         │
│  │ A │ B │ D │ F │ G │ I │   │   │   │ ← 连续内存               │
│  └───┴───┴───┴───┴───┴───┴───┴───┴───┘                         │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

#### 优点

- 无内存碎片
- 适合老年代

#### 缺点

- **移动对象需要暂停用户线程**（Stop The World）
- 整理阶段耗时较长

### 3.3 复制算法（Copying）

#### 原理

将可用内存划分为两块，每次只使用其中一块。当这一块内存用完时，将存活对象复制到另一块，然后一次性清理原块。

```
┌─────────────────────────────────────────────────────────────────┐
│                      复制算法过程                               │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  初始状态：                                                     │
│  ┌───────────────────┐  ┌───────────────────┐                 │
│  │     From 区       │  │      To 区        │                 │
│  │ ┌───┐ ┌───┐ ┌───┐ │  │                   │                 │
│  │ │ A │ │ B │ │ C │ │  │                   │                 │
│  │ └───┘ └───┘ └───┘ │  │      (空闲)        │                 │
│  │ ┌───┐ ┌───┐ ┌───┐ │  │                   │                 │
│  │ │ D │ │ E │ │ F │ │  │                   │                 │
│  │ └───┘ └───┘ └───┘ │  │                   │                 │
│  └───────────────────┘  └───────────────────┘                 │
│                                                                 │
│  标记存活对象（A, D, F）：                                      │
│  ┌───────────────────┐  ┌───────────────────┐                 │
│  │     From 区       │  │      To 区        │                 │
│  │ ┌───┐ ┌───┐ ╳───┐ │  │                   │                 │
│  │ │ A │ │ B │ │ C │ │  │                   │                 │
│  │ └───┘ └───┘ └───┘ │  │      (空闲)        │                 │
│  │ ╳───┐ ╳───┐ ┌───┐ │  │                   │                 │
│  │ │ D │ │ E │ │ F │ │  │                   │                 │
│  │ └───┘ └───┘ └───┘ │  │                   │                 │
│  └───────────────────┘  └───────────────────┘                 │
│                                                                 │
│  复制存活对象到 To 区：                                        │
│  ┌───────────────────┐  ┌───────────────────┐                 │
│  │     From 区       │  │      To 区        │                 │
│  │                   │  │ ┌───┐ ┌───┐ ┌───┐ │                 │
│  │    (空闲)         │  │ │ A │ │ D │ │ F │ │                 │
│  │                   │  │ └───┘ └───┘ └───┘ │                 │
│  │                   │  │                   │                 │
│  └───────────────────┘  └───────────────────┘                 │
│                                                                 │
│  交换 From 和 To：                                             │
│  ┌───────────────────┐  ┌───────────────────┐                 │
│  │     From 区       │  │      To 区        │                 │
│  │ ┌───┐ ┌───┐ ┌───┐ │  │                   │                 │
│  │ │ A │ │ D │ │ F │ │  │      (空闲)        │                 │
│  │ └───┘ └───┘ └───┘ │  │                   │                 │
│  └───────────────────┘  └───────────────────┘                 │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

#### 优点

1. **高效**：只复制存活对象，效率高
2. **无碎片**：分配时只需移动堆顶指针，按顺序分配
3. **无标记清除的内存碎片问题**

#### 缺点

1. **内存利用率低**：可用内存减半
2. **移动对象需要暂停用户线程**

#### 优化方案

- 新生代中 98% 的对象都是朝生夕死的
- 将新生代分为一块较大的 **Eden 区** 和两块较小的 **Survivor 区**
- 比例：Eden : Survivor : Survivor = 8 : 1 : 1
- 每次使用 Eden 和一块 Survivor，回收时将存活对象复制到另一块 Survivor

### 3.4 分代收集算法（Generational Collection）

#### 原理

根据对象存活周期的不同将内存划分为几块：
- **新生代**：对象朝生夕死，存活率低 → 复制算法
- **老年代**：对象存活率高，没有额外空间担保 → 标记-清除/标记-整理算法

```
┌─────────────────────────────────────────────────────────────────┐
│                      分代收集模型                               │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  ┌─────────────────────────────────────────────────────────┐   │
│  │                        堆                               │   │
│  │  ┌─────────────────────┬───────────────────────────┐   │   │
│  │  │       新生代        │         老年代            │   │   │
│  │  │  ┌────┬────┬────┐  │                           │   │   │
│  │  │  │Eden│ S0 │ S1 │  │                           │   │   │
│  │  │  └────┴────┴────┘  │                           │   │   │
│  │  │   复制算法          │   标记-整理/标记-清除     │   │   │
│  │  │   Minor GC          │   Full GC                │   │   │
│  │  └─────────────────────┴───────────────────────────┘   │   │
│  └─────────────────────────────────────────────────────────┘   │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

#### 对象年龄晋升

- 对象在 Eden 区出生后，经过第一次 Minor GC 仍然存活，且能被 Survivor 容纳
- 对象年龄 +1
- 当年龄达到 **MaxTenuringThreshold**（默认15）时，晋升为老年代

## 4. 垃圾收集器

### 4.1 收集器分类

```
┌─────────────────────────────────────────────────────────────────┐
│                      垃圾收集器总览                             │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│   新生代收集器              老年代收集器              全代收集器 │
│   ┌──────────┐            ┌──────────┐            ┌──────────┐ │
│   │  Serial  │───────────→│Serial Old│            │          │ │
│   └──────────┘            └──────────┘            │   G1     │ │
│   ┌──────────┐            ┌──────────┐            │   ZGC    │ │
│   │  ParNew  │───────────→│   CMS    │            │Shenandoah│ │
│   └──────────┘            └──────────┘            │          │ │
│   ┌──────────┐            ┌──────────┐            └──────────┘ │
│   │ Parallel │───────────→│Parallel  │                          │
│   │ Scavenge │            │   Old    │                          │
│   └──────────┘            └──────────┘                          │
│                                                                 │
│   连线表示可以配合使用                                          │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### 4.2 Serial 收集器

#### 特性

- 最基础、最古老的收集器
- **单线程**执行
- **Stop The World** 停顿
- 复制算法
- 客户端模式默认收集器

#### 工作原理

```
┌─────────────────────────────────────────────────────────────────┐
│                    Serial 收集器工作示意                         │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  用户线程 ─────────────────────────────→                        │
│                                                                 │
│  GC 线程                                                      │
│  ┌─────────┐                                                  │
│  │ 停止所有 │                                                  │
│  │ 用户线程 │  ← STW                                          │
│  └────┬────┘                                                  │
│       │                                                       │
│       ▼                                                       │
│  ┌─────────┐    ┌─────────┐    ┌─────────┐                   │
│  │ 标记存活 │ → │ 复制到   │ → │ 清理原   │                   │
│  │ 对象     │   │ Survivor│   │ 区域     │                   │
│  └─────────┘    └─────────┘    └─────────┘                   │
│       │                                                       │
│       ▼                                                       │
│  ┌─────────┐                                                  │
│  │ 恢复用户 │                                                  │
│  │ 线程     │                                                  │
│  └─────────┘                                                  │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

#### 参数

```bash
-XX:+UseSerialGC  # 启用 Serial 收集器
```

---

### 4.3 ParNew 收集器

#### 特性

- Serial 的多线程版本
- 并行收集（多条 GC 线程同时工作）
- **Stop The World** 停顿
- 复制算法
- Server 模式首选新生代收集器

#### 与 Serial 对比

| 特性 | Serial | ParNew |
|------|--------|--------|
| 单/多线程 | 单线程 | 多线程 |
| 适用场景 | 客户端 | 服务端 |
| 停顿时间 | 较长 | 较短（多线程并行） |

#### 参数

```bash
-XX:+UseParNewGC       # 启用 ParNew 收集器
-XX:ParallelGCThreads   # 设置 GC 线程数（默认CPU核数）
```

---

### 4.4 Parallel Scavenge 收集器

#### 特性

- 新生代收集器
- 复制算法
- **并行**收集
- **吞吐量优先**
- 自适应调节策略

#### 核心参数

| 参数 | 说明 |
|------|------|
| -XX:MaxGCPauseMillis | 最大 GC 停顿时间（期望值，不保证） |
| -XX:GCTimeRatio | GC 时间占总时间的比例（用于计算吞吐量） |
| -XX:+UseAdaptiveSizePolicy | 自动调节各区域大小比例 |

#### 与 ParNew 的区别

- ParNew：关注尽可能缩短停顿时间
- Parallel Scavenge：关注**吞吐量**（吞吐量 = 运行用户代码时间 / (运行用户代码时间 + GC时间)）

---

### 4.5 Serial Old 收集器

#### 特性

- 老年代收集器
- Serial 的老年代版本
- 单线程
- **标记-整理**算法
- Client 模式默认老年代收集器

---

### 4.6 Parallel Old 收集器

#### 特性

- 老年代收集器
- Parallel Scavenge 的老年代版本
- 多线程并行
- **标记-整理**算法
- 吞吐量优先

#### 组合使用

```bash
-XX:+UseParallelGC      # Parallel Scavenge + Serial Old
-XX:+UseParallelOldGC  # Parallel Scavenge + Parallel Old（推荐）
```

---

### 4.7 CMS 收集器（重点）

#### 特性

- 老年代收集器
- **并发**收集（用户线程和 GC 线程同时工作）
- **标记-清除**算法
- 目标是**低停顿**

#### 执行过程（4步）

```
┌─────────────────────────────────────────────────────────────────┐
│                    CMS 收集器执行过程                           │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  ┌─────────────┐                                                │
│  │  初始标记   │  STW，标记 GC Roots 直接引用的对象            │
│  │ (Initial)   │  速度快                                        │
│  └──────┬──────┘                                                │
│         │                                                       │
│         ▼                                                       │
│  ┌─────────────┐                                                │
│  │  并发标记   │  并发，从 GC Roots 向下追踪                   │
│  │(Concurrent) │  耗时长，但用户线程不停止                      │
│  └──────┬──────┘                                                │
│         │                                                       │
│         ▼                                                       │
│  ┌─────────────┐                                                │
│  │  重新标记   │  STW，修正并发标记期间变化的对象              │
│  │(Remark)    │  比初始标记慢，但比并发标记快                  │
│  └──────┬──────┘                                                │
│         │                                                       │
│         ▼                                                       │
│  ┌─────────────┐                                                │
│  │  并发清除   │  并发，清除死亡对象                          │
│  │(Concurrent) │  用户线程不停止                              │
│  │   Sweep    │  产生内存碎片                                  │
│  └─────────────┘                                                │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

#### 各阶段对比

| 阶段 | 停顿时长 | 是否并发 |
|------|----------|----------|
| 初始标记 | 短 | STW |
| 并发标记 | 无 | 并发 |
| 重新标记 | 中等 | STW |
| 并发清除 | 无 | 并发 |

#### 优点

- 并发收集，停顿时间短
- 适合对响应时间有要求的系统

#### 缺点

1. **占用 CPU 资源**：与用户线程并发，需要 CPU 资源
2. **无法处理浮动垃圾**：并发清理阶段产生的垃圾（浮动垃圾）只能等下次 GC
3. **内存碎片**：使用标记-清除算法，会产生大量碎片

#### 参数

```bash
-XX:+UseConcMarkSweepGC  # 启用 CMS 收集器
-XX:CMSInitiatingOccupancyFraction  # 触发老年代回收的阈值（默认68%）
-XX:+UseCMSCompactAtFullCollection  # FullGC 时进行碎片整理
-XX:CMSFullGCsBeforeCompaction      # 多少次 FullGC 后整理碎片
```

#### 面试提问

> **Q：CMS 收集器为什么不能处理浮动垃圾？**
>
> A：在并发清除阶段，用户线程还在运行，会继续产生垃圾。这些垃圾是并发标记之后产生的，CMS 无法在本次清理，只能等到下次 GC。这就是"浮动垃圾"。

---

### 4.8 G1 收集器（重点）

#### 特性

- **全代收集器**：可同时收集新生代和老年代
- **逻辑分代、物理不分代**：将堆划分为多个大小相等的 Region
- **可预测停顿**：可指定停顿时间
- **复制算法**
- **并发与并行**：利用多核硬件，并发清理

#### 堆结构

```
┌─────────────────────────────────────────────────────────────────┐
│                      G1 堆结构                                  │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│   ┌───┐ ┌───┐ ┌───┐ ┌───┐ ┌───┐ ┌───┐ ┌───┐ ┌───┐            │
│   │E  │ │E  │ │S  │ │O  │ │O  │ │E  │ │E  │ │O  │   → 多个  │
│   │   │ │   │ │   │ │   │ │   │ │   │ │   │ │   │     Region│
│   └───┘ └───┘ └───┘ └───┘ └───┘ └───┘ └───┘ └───┘            │
│    ↑       ↑       ↑       ↑       ↑       ↑       ↑          │
│   Eden  Survivor  Survivor  Old    Old    Eden   Eden   Old   │
│                                                                 │
│   G1 会根据停顿时间目标，动态选择回收区域                        │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

#### Region 大小

- 每个 Region 大小必须是 2 的幂，范围 1MB ~ 32MB
- 通过 `-XX:G1HeapRegionSize` 设置

#### G1 的三种 GC 模式

| 模式 | 说明 | 触发条件 |
|------|------|----------|
| Young GC | 新生代垃圾回收 | Eden 区满 |
| Mixed GC | 新生代 + 部分老年代 | 晋升阈值 |
| Full GC | 整个堆回收 | Mixed GC 效果不佳 |

#### 工作原理

```
┌─────────────────────────────────────────────────────────────────┐
│                    G1 收集器工作原理                             │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  1. Young GC                                                   │
│     - 回收所有年轻代 Region                                     │
│     - STW                                                     │
│     - 并行执行                                                │
│                                                                 │
│  2. 并发标记周期                                               │
│     - 初始标记：STW，标记根 Region                             │
│     - 根Region扫描：扫描 Survivor 区                          │
│     - 并发标记：并发标记所有 Region                            │
│     - 重新标记：STW，修正标记                                  │
│     - 独占清理：STW，计算各 Region 价值                        │
│                                                                 │
│  3. Mixed GC                                                  │
│     - 选择价值最高的 Region 回收                               │
│     - 包括年轻代 + 选中的老年代 Region                         │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

#### Remembered Set（记忆集）

- 解决 Region 之间的引用问题
- 每个 Region 维护一个 RSet，记录其他 Region 对本 Region 的引用
- 避免全堆扫描

#### 参数

```bash
-XX:+UseG1GC              # 启用 G1 收集器
-XX:MaxGCPauseMillis      # 设置目标停顿时间（默认200ms）
-XX:G1HeapRegionSize      # 设置 Region 大小
-XX:InitiatingHeapOccupancyPercent  # 触发并发标记周期阈值
-XX:G1NewSizePercent      # 年轻代最小比例（默认5%）
-XX:G1MaxNewSizePercent    # 年轻代最大比例（默认60%）
```

#### 适用场景

- 服务器端应用
- 大堆内存应用（6GB+）
- 追求低停顿时间

#### 面试提问

> **Q：G1 和 CMS 的区别？**
>
> | 特性 | CMS | G1 |
> |------|-----|-----|
> | 算法 | 标记-清除 | 复制算法 |
> | 内存碎片 | 有碎片 | 无碎片 |
> | 停顿时间 | 不可控 | 可预测 |
> | 全代/老年代 | 仅老年代 | 全代 |
> | Region | 不适用 | 逻辑分代、物理不分代 |

> **Q：G1 为什么能实现可预测停顿？**
>
> A：G1 将堆划分为多个 Region，可以根据每个 Region 的回收价值（回收获得的空间和回收所需时间的比值）优先回收价值最高的 Region，从而在指定停顿时间内获得最大回收效果。

### 4.9 ZGC（Zero GC）

#### 特性

- JDK 11+ 可用
- **并发**标记和压缩
- **着色指针**技术
- 不分代（逻辑上仍然可以分代，但物理上不分）
-停顿时间极短（亚毫秒级）

#### 原理

- 使用着色指针（Colored Pointers）标记对象
- 64位指针中，使用几位作为标记位
- 读屏障（Load Barrier）实现并发移动对象

---

### 4.10 收集器对比总结

| 收集器 | 作用区域 | 算法 | 停顿时间 | 吞吐量 | 并发 |
|--------|----------|------|----------|--------|------|
| Serial | 新生代 | 复制 | 长 | 低 | 单线程 |
| ParNew | 新生代 | 复制 | 中 | 中 | 多线程 |
| Parallel Scavenge | 新生代 | 复制 | 中 | 高 | 多线程 |
| Serial Old | 老年代 | 标记-整理 | 长 | 低 | 单线程 |
| Parallel Old | 老年代 | 标记-整理 | 中 | 高 | 多线程 |
| CMS | 老年代 | 标记-清除 | 短 | 中 | 并发 |
| G1 | 全代 | 复制 | 可预测 | 高 | 并发 |
| ZGC | 全代 | 着色指针+复制 | 极短 | 高 | 并发 |

## 5. GC 进阶知识

### 5.1 对象进入老年代的时机

1. **年龄阈值**：对象年龄达到 MaxTenuringThreshold（默认15）
2. **动态年龄判定**：Survivor 中相同年龄对象大小总和 > Survivor 空间的一半，年龄 >= 该年龄的对象直接进入老年代
3. **大对象**：-XX:PretenureSizeThreshold 设置大对象阈值，超过直接分配在老年代

### 5.2 Minor GC vs Full GC

| 特性 | Minor GC | Full GC |
|------|----------|---------|
| 触发区域 | 新生代 | 老年代 + 方法区 |
| 触发条件 | Eden 区满 | 老年代满/显式调用/方法区满 |
| 停顿时间 | 短 | 长 |
| 频率 | 高 | 低 |

### 5.3 Stop The World（STW）

- GC 过程中，暂停所有用户线程
- 是 GC 停顿的主要原因
- 优化目标：减少 STW 时间

## 6. 常见面试问题汇总

### 问题与答案

| 问题 | 答案 |
|------|------|
| 如何判断对象是否需要回收？ | 可达性分析，从 GC Roots 向下搜索，无引用链则可回收 |
| GC Roots 有哪些？ | 虚拟机栈、方法区静态/常量、本地方法栈、JVM 内部引用 |
| 垃圾回收算法有哪些？ | 标记-清除、标记-整理、复制、分代收集 |
| 为什么新生代用复制算法？ | 新生代对象大多朝生夕死，存活率低，复制效率高 |
| CMS 收集器执行过程？ | 初始标记→并发标记→重新标记→并发清除 |
| CMS 的缺点？ | 产生内存碎片、浮动垃圾、占用CPU资源 |
| G1 的特点？ | 逻辑分代物理不分代、Region设计、可预测停顿 |
| 对象何时进入老年代？ | 年龄达到阈值、动态年龄判定、大对象直接分配 |
| 常用 GC 参数？ | -XX:+UseSerialGC、-XX:+UseG1GC、-Xms、-Xmx |
