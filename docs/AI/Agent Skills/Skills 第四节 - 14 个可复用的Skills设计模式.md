## 二、正文

在 Agent Skills 的生态中，技能大致可以分为两类：

1. **任务型技能**（通常设置 disable-model-invocation: true）：对应一整套步骤化流程，比如部署、提交或安全审查，用户一般通过 /skill-name 直接触发。
2. **参考型技能**（用户不可直接调用）：更像是背景知识，比如风格指南或领域术语，Claude 会在相关场景下自动应用。

本文基于 Anthropic 官方的技能编写最佳实践，总结了 **14 个可以复用的设计模式**，分为五类：

1. 发现与选择
2. 上下文经济
3. 指令校准
4. 工作流控制
5. 可执行代码

## 发现与选择

> 技能写出来没人用，写得好有什么意义？前两个模式要解决的，就是这个「怎么被用到」的问题。

### 1. 激活元数据模式（Activation Metadata pattern）

当你的技能库里有几十个技能时，Claude 怎么知道该用哪一个？

答案就在 description。但很多人把它当成「摘要」，写成类似“用于处理文档”这种模糊描述。结果就是：要么选错，要么干脆不用。

description 不是摘要，而是 Claude 做选择时最关键的信号。

在会话开始时，Claude 只能看到每个技能的 name 和 description。如果这一步没选对，后面写得再好也用不上。

一个好的 description，通常要包含三点：

1. 做什么（功能）
2. 什么时候用（触发场景）
3. 遇到哪些词要触发（关键词）

Anthropic 的 skill-creator 甚至建议把 description 写得「更主动」一点，因为 Claude 本身有点「触发不够」的倾向。例如：

“即使用户没有明确提到仪表盘，只要提到数据可视化或内部指标，就应该触发这个技能”。

![image-20260814101750118](E:\CodeRepositroy\myWebBlog\docs\AI\Agent Skills\image\image-20260814101750118.png)

**适用场景**：所有技能都应该用这个模式。入口没做好，后面都没意义。

**权衡点**：在开放的 Agent Skills 规范中，description 上限是 1024 字符；在 Claude Code 里，description 和可选的 when_to_use 一起最多 1536 字符。空间有限，每句话都要在「触发词、排除条件和领域关键词」之间做取舍。

### 2. 排除条款模式（Exclusion Clause pattern）

只说「什么时候用」还不够，还要说明「什么时候不用」。

比如你同时有一个「文档处理」和一个「代码生成」技能，如果它们都写成「处理所有文本相关任务」，Claude 很难判断该选哪个。

正向触发是把它拉进来，排除条款是把它推出去。

Ruben Hassid 把排除条款称为「description 里最关键的一行」，甚至比正向触发更重要。

一个好的排除条款，通常会说清楚：

1. 哪些场景不适用
2. 哪些内容更应该交给其他技能
3. 哪些情况直接用 Claude 就够了

示例：

“不要用于博客文章、通讯邮件、推文或长篇内容。”

![image-20260814101816340](E:\CodeRepositroy\myWebBlog\docs\AI\Agent Skills\image\image-20260814101816340.png)

**适用场景**：几乎所有技能，尤其是和其他技能有重叠的那些。

**权衡点**：维护成本。技能一多，排除条款也需要跟着调整，否则容易出现冲突或空白区。

## 上下文经济

> 上下文窗口是个共享资源，每个 token 都在和其他技能、对话历史以及当前请求抢空间。

### 3. 上下文预算模式（Context Budget pattern）

很多技能喜欢从头解释一遍：什么是 PDF、什么是库、JSON 是怎么工作的——但这些 Claude 本来就知道。

这种冗余在几十个技能里重复出现，上下文窗口在用户开口之前就被占掉一大半。

核心理念：**Claude 是聪明的**。每段话都要配得上它占用的 token。如果删掉一句话不会让「足够聪明的读者」困惑，那它大概率就是多余的。

额外注意点：

1. 术语要统一：选一个说法就一直用，比如只用 field，不要来回切换 field / box / element
2. 避免时间敏感表达：像“2025 年 8 月之前”这种描述，很快就会过时。更好的做法是把这类信息放到「旧模式」的附录里

![image-20260814102136493](.\image\image-20260814102136493.png)

**适用场景**：所有技能的基础要求，可以当作默认纪律。

**权衡点**：如果技能要兼容多个模型，就要按最弱模型来决定细节程度——对 Sonnet 来说刚好的简洁，对 Haiku 可能偏简略。

### 4. 渐进式披露模式（Progressive Disclosure pattern）

很多人会把所有内容一股脑塞进 SKILL.md：不管用户问什么，几百行甚至上千行内容一次性全加载。

核心思路：把 SKILL.md 当成目录，而不是仓库。

做法：

1. 主文件尽量控制在 500 行以内
2. 把细节拆到不同文件（例如 FORMS.md、REFERENCE.md、reference/finance.md）
3. 只在需要时再加载这些文件

实用技巧：

1. scripts/ 里的脚本可以执行，但不会被加载进上下文
2. 对于特别长的参考文件，在顶部加目录（TOC），让 Claude 知道整体结构

![image-20260814102203990](.\image\image-20260814102203990.png)

**适用场景**：当 SKILL.md 超过 ~300 行时，基本就该考虑拆分。

**权衡点**：拆分带来的复杂度。文件多后，Claude 需要判断下一步该加载哪个文件，一旦选错，多走几轮。

## 指令校准

> 指令到底该写多细？写得太死，会限制发挥；写得太松，又容易跑偏。下面几个模式在两者之间找平衡。

### 5. 控制调优模式（Control Tuning pattern）

有些技能会把每一步都写死，结果遇到灵活情况时 Claude 被卡住。

核心：**根据任务的脆弱程度决定指令严格度**

自由度示例：

1. 高自由度（文本指令，例如“用你的判断”）：适合开放型任务，如代码审查
2. 中自由度（伪代码、参数化步骤）：适合有流程但需灵活调整，如部署
3. 低自由度（精确脚本、强约束，例如“不要修改”）：适合高风险操作，如数据库迁移

语气也是调节手段，例如：设定角色：“你是一个更关注正确性而不是风格的资深代码审查员”。

![image-20260814102225033](.\image\image-20260814102225033.png)

**适用场景**：对每个步骤都问一句——这里允许多少偏差？

**权衡点**：写死一点并非更安全，只是把失败方式从「做错」变成「做不了」。

### 6. 解释原因模式（Explain-the-Why pattern）

把规则写成一串 ALWAYS / NEVER / MUST，看起来很清晰，但其实缺少上下文。Claude 可能会按字面执行，却在边界情况里用错，或者在不该严格执行的时候也机械套用。

Anthropic 的 skill-creator 甚至把这种全大写指令当作需要重构的信号。

这个模式的核心是：**先说规则，再说明原因。**

这样 Claude 不只是「照做」，而是能理解背后的逻辑，在规则没覆盖到的情况里也能自己做判断。

比如：“使用构造器注入。字段注入会破坏可测试性，因为需要依赖 Spring 上下文来模拟字段。” 就比： “必须使用构造器注入，绝不使用字段注入。” 更稳一些。前者提供了推理依据，后者只是限制行为。

![image-20260814102358549](.\image\image-20260814102358549.png)

**适用场景**：写 MUST / ALWAYS / NEVER 的强制性规则时

**权衡点**：解释消耗 token。低自由度场景可直接命令式；需要判断的地方用解释原因更合适。

### 7. 模板脚手架模式（Template Scaffold pattern）

像报告、提交信息、API 请求、发布说明这类输出，只要结构很重要，Claude 每次生成的「形状」往往都不太一样。

问题在于：结构其实藏在示例里，但技能本身没说清楚，所以每次都在重新「猜」。

这个模式的做法很直接：**给一个带占位符的模板，让它按结构填空。**

做法：**提供带占位符的模板**

1. 严格模板（必须按结构来）：适合数据契约、机器解析
2. 灵活模板（推荐结构，可调整）：适合文档类输出

理解方式：模板定结构，示例定风格。

![image-20260814102419785](.\image\image-20260814102419785.png)

**适用场景**：只要输出有固定结构，或者后面还要被解析（不管是人还是程序），就应该用模板。

**权衡点**：模板越严格，越容易限制表达。在一些边缘情况里，反而可能不够用。所以如果不是给机器用，优先用灵活模板。

### 8. 技能内示例模式（In-Skill Examples pattern）

光靠描述，很难把语气、格式和细节说清楚。常见情况是：结构对了，但风格不对——比如提交信息用了正确的 conventional commit 前缀，但语气跟团队不一致。

这个模式的做法是：在技能里放几个输入 / 输出示例，让它照着对齐。

Input: [用户输入示例]  

Output: [期望输出示例]

和 few-shot 类似，给两到三个例子，通常比一大段说明更管用。Claude 会优先对齐示例，而不是从文字里自己猜。

**理解方式**：模板（上一个模式）解决的是结构问题；示例解决的是风格问题。两者配合使用时效果最好：模板定结构，示例定风格。

![image-20260814102441341](.\image\image-20260814102441341.png)

**适用场景**：既有结构要求、又有表达风格要求的输出，比如提交信息、发布说明、changelog、审查摘要等。

**权衡点**：Claude 很容易「学例子」。如果示例里带了某种习惯，它会在所有输出里复现。所以示例要尽量覆盖不同情况，而不是只给一种写法。

### 9. 已知陷阱模式（Known Gotchas pattern）


很多技能只覆盖「正常流程」，告诉 Claude 该怎么做，却没说哪些地方容易出错。

一旦遇到真实环境里的边缘情况——字段不存在、命令在 macOS 能跑但在 Linux 失败、库悄悄返回空结果——Claude 没有参考，就容易自己「编一个修复」。

做法：**专门列出已知的陷阱**

在 SKILL.md 里单独加一节，把常见失败情况写清楚，例如：

1. “扫描 PDF 可能返回空数组，需要先检查页码类型”
2. “页面旋转必须在列提取前设置 page.rotation = 0”

在实战里，这一部分往往是一个技能最有价值的内容，因为它直接来自踩过的坑。

**适用场景**：已经在真实环境跑过一段时间的技能，可以根据实际问题不断补充。

**权衡点**：这些「陷阱」会变化。库升级、API 改动后，旧问题可能不存在，如果不更新，反而误导 Claude 去排查已经不存在的错误。

## 工作流控制

> 多步骤流程该怎么控制？从简单的线性步骤，到带校验的执行，再到基于计划的流程控制，复杂度逐步增加。

### 10. 执行清单模式（Execution Checklist pattern）

在多步骤流程里，常见问题不是做错，而是没做完：跳过验证、忘了当前进度，甚至提前宣布完成——「应该已经好了」，但其实只做到一半。

做法：**把流程变成一份可勾选的清单**

在对话中直接使用，例如：

```
- [ ] 步骤1：...
- [ ] 步骤2：...
- [ ] 步骤3：...
```

每完成一步就勾掉，未完成的会一直保留。

关键点：**未完成的项是可见的**，用户和 Claude 都能看到进度。

![image-20260814102547741](.\image\image-20260814102547741.png)

**适用场景**：超过三步的流程，尤其是那些「少一步就可能出问题」的场景。

**权衡点**：清单每轮都会完整出现，长对话里 token 会明显增加。短流程使用可能显得冗重。

### 11. 自纠正循环模式（Self-Correcting Loop pattern）

在生成代码、编辑 XML、或按规范写文档时，单次输出容易留下问题，而这些问题本来是技能可以发现的。

问题不在于「怎么写对」，而在于：没有人检查它写得对不对。

做法：**引入显式循环**

流程：生成 → 验证 → 失败则修复 → 再验证

验证可以是：

1. 脚本（例如 python validate.py fields.json）
2. 或规则检查（例如重新对照 STYLE_GUIDE.md 一条条过）

只有通过验证，流程才结束。

![image-20260814102605253](.\image\image-20260814102605253.png)

**适用场景**：对质量要求高、且可验证的任务，如代码生成、配置文件、结构化输出等。

**权衡点**：可能不收敛。如果验证不够严格，Claude 一直出错，会反复循环。需设置重试上限，失败时回退给用户处理。

### 12. 计划-验证-执行模式（Plan-Validate-Execute pattern）

对于批量或高风险操作——如批量改表结构、数据迁移、整篇文档重写——如果直接「上来就做」，一旦出错，很容易一路错到底。

等你发现问题时，修改可能已应用完，回滚成本高。

做法：**在「理解任务」和「执行操作」之间，加一层可验证的中间产物**

1. 通常是结构化计划（如 JSON）
2. 流程：计划 → 验证 → 通过后执行
3. 所有验证都在副作用之前完成

区别于自纠正循环：自纠正是在结果出来后修复，这里是在执行前阻止错误。

![image-20260814102624660](.\image\image-20260814102624660.png)

**适用场景**：批量操作、不可逆操作或代价高的任务。

**权衡点**：流程更重。简单任务可能成本大于收益，更适合高风险任务。

## 可执行代码

把部分工作从 Claude 的推理中拿出来，交给确定性脚本去执行：运行、返回结果——要么成功，要么失败。

### 13. 实用工具包模式（Utility Bundle pattern）

如果每次都让 Claude 临时写验证脚本、PDF 解析器或数据处理逻辑，不仅慢，还不稳定，而且这些「临时代码」消耗 token。

做法：**把确定性能力提前做成脚本，放到 scripts/**

Claude 之后通过 bash 调用，而不是每次写一遍。优点：上下文只占用脚本输出，而非实现细节。

脚本基本要求：

1. 能处理常见错误，而不是把问题丢回 Claude
2. 要么提供合理默认值，要么快速失败并说明原因
3. 常量要写清楚用途（避免魔法数字，例如“30s 超时覆盖慢连接”）

![image-20260814102647483](.\image\image-20260814102647483.png)

**适用场景**：确定性强、频繁重复、值得单独测试的操作。

**权衡点**：环境依赖。不同机器、系统表现可能不同。需在 SKILL.md 写清依赖，尽量避免平台问题。

### 14. 自主校准模式（Autonomy Calibration pattern）

如果一个技能默认拿到整套工具，它理论上什么都能做：写文件、跑 shell、调外部服务——哪怕任务只是读取数据。

做法：**在 YAML 中明确 allowed-tools**，只开放真正需要的能力，例如：

1. 安全审计：Read, Grep, Glob
2. 文档生成：Read, Write
3. 部署任务：只开放受限命令的 Bash

注意：allowed-tools 是预批准，不是硬限制。真正约束需靠权限策略。

**适用场景**：只需要少量能力的技能，尤其是安全、审计、分析类任务。

**权衡点**：容易误用。如果写得太宽，放大权限；需配合权限策略严格控制。

## 总结

这 14 个模式基本覆盖了技能设计中最容易出问题的关键点：

1. description 决定技能会不会被用到
2. 渐进式披露决定技能占用多少上下文
3. 解释原因和已知陷阱决定 Claude 在边界情况下能否正确判断
4. 计划-验证-执行和自主校准控制风险

每个模式背后都对应一种常见失败方式。
